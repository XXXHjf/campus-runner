# 二手交易接口与流程

本文维护二手交易当前稳定行为。具体字段仍以运行中的 OpenAPI 文档为准。

## 首页学校标识

二手首页将品牌与学校名称放在同一行，搜索框独占下一行。按当前账号
`GET /api/user` 的 `schoolId` 匹配 `GET /api/school` 列表中的 `id`、`schoolName`，
沿用校园认证页的名称来源；当前用户查询虽然声明了 `schoolName`，实际并未填充，
不能依赖它直接显示。不得使用示例学校或商品自提位置推断所属学校。
只有有效登录态、已保存的学校 ID 且能匹配非空校名时才显示学校及分隔线；未登录、
仅完成资料注册但尚未填写学校、学校资料缺失时一起隐藏。校名只说明所属学校，
不代表校园认证审核通过，也不改变现有商品查询和业务权限。注册与认证的区别见
`docs/api/user-onboarding.md`。

每次返回首页及下拉刷新时重新读取学校信息；首次启动等待已有静默登录完成，
无须用户重启。退出或更换账号时清除旧校名，离页和重叠请求的过期结果不得覆盖
当前显示。校名读取失败时隐藏标识，不阻断商品加载，也不弹出额外提示。
学校与分隔线的显隐不改变标题行高度，长名称单行省略并为微信菜单胶囊保留空间。

轻量检查：`node --test tests/mini-program/secondHandHomepage.test.cjs`。开发者工具中
另行检查无学校/有学校、注册及填写学校后返回、退出登录、长校名和搜索交互。
回滚时仅恢复首页的布局和校名读取逻辑；不涉及接口、数据库或注册认证流程变更。

## 商品列表筛选

`GET /api/second-hand/products` 支持组合使用以下首页筛选参数：

- `categoryId`：商品分类 ID；
- `pickupAddressPrefix`：发布商品时保存的自提点前缀，格式为
  `校区 类型 楼栋`；
- `keyword`：商品标题或描述关键词。

自提位置使用商品发布时固化的 `pickup_address_snapshot`，不关联地址簿的当前值。这样卖家
之后修改或删除地址簿记录时，已发布商品仍按当时向买家展示的自提点参与筛选。查询只匹配
完整的 `校区 类型 楼栋`，以及紧随其后的详细地址，避免名称相近的楼栋互相误匹配。

验证时至少覆盖“分类 + 自提位置”组合查询、仅分类查询和不选择自提位置三种情况。若需
回退此能力，可停止传递 `pickupAddressPrefix` 并移除 Mapper 中对应条件，不涉及数据库迁移
或历史数据回滚。

## 商品收藏

收藏对象是二手商品，不是已经生成的交易订单。用户可从商品详情收藏或取消收藏，并从个人
中心进入“我的收藏”。卖家不能收藏自己的商品。

- `POST /api/second-hand/products/{id}/favorite`：收藏商品；重复调用保持已收藏，不重复计数。
- `DELETE /api/second-hand/products/{id}/favorite`：取消收藏；重复调用保持未收藏，计数不减为负数。
- `GET /api/second-hand/favorites`：按最近收藏时间获取当前用户的收藏商品。
- `GET /api/second-hand/products/{id}`：响应中的 `favorited` 表示当前用户是否已收藏，
  `favoriteCount` 表示当前有效收藏数。

已售出或已下架的商品仍保留收藏关系并在列表中展示当前状态；逻辑删除的商品不再显示。
收藏关系由 `tb_second_hand_favorite` 的“用户 + 商品”唯一索引防止重复，商品表的
`favorite_count` 在同一事务中同步更新。数据库迁移、校验和回滚见
`docs/database/second-hand-favorite-migration.md`。

### 我的收藏：离页提交取消

为避免误触后商品立即消失，“我的收藏”页的取消操作先仅改变页面内的选择：卡片保留
原位置，按钮从“取消收藏”切换为“收藏”；再次点击即撤销本次取消，不发送重复收藏请求。
页头数量跟随当前选择变化，即使全部点了取消，也保留卡片供用户恢复。

仅在该页 `onUnload` 时提交最终待取消的商品，沿用现有 DELETE 接口。下拉刷新、打开
详情后返回及切到后台不会提前提交；待取消状态在本次页面实例内保留。商品详情本身的
收藏行为不变，仍直接调用现有接口。小程序被系统强制结束时不保证触发卸载和完成请求，
重新进入时以服务端返回的收藏关系为准，不把尚未提交的选择当作成功结果。

收藏写请求在公共服务中按调用顺序执行；重新进入收藏列表及读取详情前等待已提交的
写请求完成，防止快速重进读到取消前的列表或后发收藏被先发取消覆盖。单项取消失败不
阻断其他商品，显示中文失败提示；下次进入时失败商品仍按实际收藏状态显示，可再次操作。
已卸载页面不再接收异步列表结果，重叠刷新以最后一次请求为准。

验证命令：`node --test tests/mini-program/secondHandFavorites.test.cjs`。覆盖取消后恢复、
全部取消仍保留列表、刷新/详情返回、退出提交、快速重进、部分失败、写入顺序及卸载后的
异步回调。开发者工具还需检查按钮不触发卡片跳转，以及两种状态在窄屏下的布局。
回退时同时恢复收藏页和公共服务的时序处理；接口和数据库结构不变，无需迁移。

## 当前交易模式

系统配置 `second_hand_trade_mode` 当前必须为 `OFFLINE`。平台只提供商品展示、私信、议价、
下单和交付记录，付款与交付由双方自行协商；平台不代收、不担保、不退款，也不从二手货款
中抽取服务费。

新订单保存 `tradeMode=OFFLINE`，创建后直接进入状态 `1`（待交付），商品进入交易中。卖家
标记交付后进入状态 `2`，买家确认双方已完成商品和款项交接后进入状态 `3`。交付前买卖双方
都可以取消订单，订单进入状态 `4`，商品恢复在售。线下订单不会自动确认完成。

交付方式继续支持买家自提和卖家配送。选择卖家配送时，订单保存买家地址簿 ID 和配送地址
快照；后续修改地址簿不会改变已经下单的配送信息。

订单上的 `payAmount` 和 `sellerIncome` 是为兼容旧数据保留的金额字段；在线下模式中都等于
双方约定价，不表示平台已经收款或结算。`serviceFeeRate` 和 `serviceFee` 固定为 `0`。

旧支付、退款和卖家转账代码继续用于 `tradeMode=ONLINE` 的历史订单善后。当前模式下
`POST /api/second-hand/pay/jsapi/{orderId}` 会拒绝发起新的微信支付。重新开放线上能力前，必须
重新核对微信正式准入、资金关系和接口版本，不能只修改配置值。

### 历史服务费配置

`second_hand_service_fee_rate` 仅供历史线上交易兼容，当前管理端隐藏该配置。

- `GET /admin/api/config/second_hand_service_fee_rate`：读取二手交易服务费率。
- `PUT /admin/api/config/second_hand_service_fee_rate`：修改费率，请求字段为
  `secondHandServiceFeeRate`，允许范围为 `0` 到 `1`。

跑腿业务的 `service_fee_rate` 和 `service_fee_min` 不参与二手订单计算；二手交易当前没有
最低服务费配置。

## 订单创建的非空字段约束

`tb_second_hand_order.transfer_attempt` 是 `NOT NULL DEFAULT 0`。如果订单插入语句显式包含
该列，订单实体必须把它初始化为 `0`；显式插入 `NULL` 时数据库默认值不会生效。

订单构造必须初始化 `transferAttempt=0`，Mapper 同时使用 `COALESCE` 防止显式写入空值。
验证必须同时覆盖直接下单和接受议价，确保两条路径都可以创建线下订单：

- 使用真实 `NOT NULL` 表结构分别验证直接下单和接受议价，不能只做 Mock 单元测试。

接受议价在事务中先创建订单、再更新议价状态，因此插入失败时事务应整体回滚；修复后需
验证失败期间没有遗留“已接受但无订单”的记录。

## 私信会话

私信按“商品 + 对方用户”组成一对一会话，买家可从商品详情联系卖家，卖家只能回复已有
互动的买家。消息仍保存商品和可选订单关联，便于交易双方在同一个会话里持续沟通。

- `POST /api/second-hand/messages`：发送私信。
- `GET /api/second-hand/conversations`：获取当前用户的会话列表及未读数。
- `GET /api/second-hand/conversations/{productId}/{counterpartyId}/messages`：获取一对一消息并
  将当前用户收到的消息标记为已读。

旧的 `GET /api/second-hand/products/{id}/messages` 暂时保留兼容，不作为新版小程序的会话入口。

## 联系方式

订单详情仅向订单买卖双方开放。线下订单创建后，详情响应的 `counterpartyPhone` 返回对方
当前手机号；下单前只能使用私信。小程序默认脱敏展示，仅在用户主动拨号时使用完整号码。
历史线上订单仍以支付成功作为开放电话的边界。

## 历史线上订单的卖家收款

以下内容只适用于 `tradeMode=ONLINE` 的历史订单，不适用于新线下订单。

买家确认收货后，订单进入收款处理中。后端使用独立 `transfer_out_bill_no` 发起微信商家
转账，并保存微信状态、转账单号和确认收款参数。结果不确定时保留处理中，由定时任务查询，
不会直接判定为失败。

当微信返回 `WAIT_USER_CONFIRM` 时，卖家调用
`GET /api/second-hand/orders/{id}/transfer-claim` 获取 `mchId`、`appId` 和 `packageInfo`，
再由小程序调用 `wx.requestMerchantTransfer`。小程序成功拉起页面只表示确认页已打开，最终
到账以微信回调或后端查询到 `SUCCESS` 为准。

管理员对收款中订单执行“同步收款状态”，只查询当前转账；对收款失败订单执行“重新发起
收款”才会生成新的商户单号，避免重复付款。

### 转账错误分类与存量订单恢复

微信商家转账场景 `1010` 必须先在生产商户号中获批。当前生产版本存在已确认但尚未修复的
偏差：创建转账返回确定性的 `4xx INVALID_REQUEST` 时也会写成 `QUERY_REQUIRED`；随后查询
未创建的微信转账单只得到 `404`，但订单不会退出收款中，卖家也拿不到
`WAIT_USER_CONFIRM` 所需的 `packageInfo`。

整改必须区分以下结果：

- 参数、权限或场景未开通等确定性 `4xx` 立即进入收款失败，并保存面向管理员的可操作原因；
- 网络中断、超时、`5xx` 等无法确认微信是否受理的结果才进入 `QUERY_REQUIRED`；
- 查询 `404` 不能无限保持收款中。若已有确定性创建失败证据，应立即转失败；其他情况采用
  有上限的重试并进入人工核对，避免重复付款。

恢复存量订单前必须先核对微信侧没有生成转账单。确认未创建后，将原尝试标记失败；待场景
获批且错误分类逻辑上线后，再通过管理员“重新发起收款”生成新的商户单号。若无法确认微信
是否受理，不得直接重试。

验证至少覆盖：确定性 `INVALID_REQUEST` 进入失败、未知网络结果保持可查询、
`WAIT_USER_CONFIRM` 返回完整确认参数、查询 `404` 能在规定边界内退出，以及重试生成新商户
单号但不重复付款。


## 二手订阅消息

通知跟随现有 OFFLINE 交易流程；不改变历史 ONLINE 支付、退款和转账逻辑。
本次不新增卖家还价，拒绝议价也不发送“还价”通知。

| 成功事件 | 接收方 | 模板 B 状态 | 跳转 |
| --- | --- | --- | --- |
| 买家直接下单 | 卖家 | 新订单 | 订单详情 |
| 买家议价 | 卖家 | 议价中 | 商品详情 |
| 卖家接受议价并生成订单 | 买家 | 待交付 | 新订单详情 |
| 卖家标记交付 | 买家 | 待确认 | 订单详情 |
| 买家确认完成 | 卖家 | 已完成 | 订单详情 |
| 买家取消 | 卖家 | 已取消 | 订单详情 |
| 卖家取消 | 买家 | 已取消 | 订单详情 |
| 新私信 | 接收者 | 模板 A 新留言消息 | 与发送者的商品会话 |

模板 B 使用 `character_string1 / phrase2 / time3 / thing4 / short_thing5`。
卡片订单编号是 `orderNumber`，详情路径 `id` 必须是订单主键，不能传业务订单号。
议价尚未生成订单，编号和跳转均使用商品 ID。模板 A 使用
`thing1 / thing2 / time3 / thing4 / thing5`，会话路径中的 `counterpartyId` 为发送者 ID。
用户名、正文、商品来源和提示最多 20 个字符；短标题保守限制为 5 个字符，优先提取
商品名称关键词，未知商品去除成色和促销词后截断，空值使用中文兜底。

小程序在发布成功、下单成功、议价成功后请求订单模板；会话发送成功后请求留言模板。
编辑商品不重复请求。拒绝、接口不可用或授权失败不改变已成功的业务结果。
这些授权是接收后续通知的机会，不能视为一次授权覆盖整个交易所有通知：
一次性订阅额度可能耗尽，卖家在发布时取得的额度也可能先被议价通知消耗。
最终是否弹窗和是否可送达仍须以微信真机与后台模板配置验证。

模板 ID 集中于小程序 `services/subscriptionService.js` 与服务端 `WeChatProperties`；
更换模板时两端同步更新，服务端属性为 `second-hand-order-template-id` 和
`second-hand-message-template-id`。两端模板 ID 已按用户提供的微信后台原文核对；更换模板后仍须同步两端并真机验证。

发送在事务提交后进入有界内存队列，事务回滚不发送，微信延迟和失败不阻塞业务响应。
发送方缓存 access token，并仅在微信明确返回 token 失效时重取一次；网络超时不盲目重发，
避免重复消耗额度。日志仅记录错误类别或微信错误码，不记录 token、私信正文及收件人标识。
当前是尽力通知，队列满、进程中断或微信拒绝可能丢失通知，不提供持久补发保证。

验证：运行 `SecondHandSubscriptionServiceTest`、`SecondHandOfflineTradeServiceTest`、
`TakeOrderSubscriptionTest` 和 `tests/mini-program/subscriptionService.test.cjs`。
真机使用买卖双方账号核对弹窗、接收方、内容和跳转，额外测试拒绝授权、重复操作、额度耗尽。
如需回滚，应同时回退小程序授权入口和服务端通知接入；无新增数据库结构。

### 跑腿通知复查

跑腿保留原有接单、取件、送达三个模板。通知改由服务端成功状态变更在提交后触发，
不再依赖小程序额外调用发送接口；旧 `/api/message/*` 请求保留成功空响应，避免旧版本重复发送。
状态更新拦截重复操作和逆向流转。通知提示改为中文并限制 thing 长度，发送通道与二手共用。
若回滚服务端自动触发，需要同步恢复小程序发送调用，避免出现漏发。
