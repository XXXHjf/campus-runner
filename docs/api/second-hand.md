# 二手交易接口与流程

本文维护二手交易当前稳定行为。具体字段仍以运行中的 OpenAPI 文档为准。

## 2026-10-11 内容审核核验与本批范围

当前商品发布/编辑直接生效；媒体用途、归属、大小和解码校验不是内容审核。仓库未发现商品文本/图片外部审核调用或商品审核状态链路；微信/OSS 控制台及外部人工审核未核实，不能断言外部不存在审核。管理员已有商品状态修改、逻辑删除与留言删除；进行中交易会限制商品管理变更，普通下架可被卖家重新上架，详情也未按下架状态隔离，因此不能把普通下架表述为审核封禁。

用户在设计确认后明确撤回举报和本批前端改动，要求跳过此项。已撤回本次商品版本审核、举报/申诉、独立隔离代码、设计稿与数据库迁移；没有新增页面，也没有执行审核迁移。此项记为用户指定跳过，不标记已整改。将来若继续，按用户方向优先讨论提交订单/发布环节的审核，明确审核对象、渠道、失败处理、历史订单及资金影响，再单独确认实施；本批不自动加任何新审核流程。

## 游客浏览与身份操作

GET 分类、商品列表和数字 ID 的商品详情允许游客访问；有效登录身份仍用于学校筛选、
收藏状态和本人商品识别。游客不请求个人资料。订单、议价、私信、个人商品与收藏列表不公开。
下单、发布、议价、收藏和联系卖家入口检查登录及现有校园认证要求；取消留在当前页面，
未认证提供去认证、审核中提供查看进度、驳回提供重新提交指引。服务端仍执行身份和认证校验。
服务端未认证错误使用中文，请求层兼容旧版本的英文错误，避免截断成无法理解的 Toast。
完整登录、返回、验证及回滚规则见 [用户登录与校园认证](user-onboarding.md)。

## 首页学校标识

二手首页将品牌与学校名称放在同一行，搜索框独占下一行。按当前账号
`GET /api/user` 的 `schoolId` 匹配 `GET /api/school` 列表中的 `id`、`schoolName`，
沿用校园认证页的名称来源；当前用户查询虽然声明了 `schoolName`，实际并未填充，
不能依赖它直接显示。不得使用示例学校或商品自提位置推断所属学校。
只有有效登录态、已保存的学校 ID 且能匹配非空校名时才显示学校及分隔线；未登录、
仅完成资料注册但尚未填写学校、学校资料缺失时一起隐藏。校名只说明所属学校，
不代表校园认证审核通过，也不改变现有商品查询和业务权限。注册与认证的区别见
`docs/api/user-onboarding.md`。

每次返回首页及下拉刷新时重新读取学校信息；游客启动不登录、不显示校名。
退出或更换账号时清除旧校名，离页和重叠请求的过期结果不得覆盖
当前显示。校名读取失败时隐藏标识，不阻断商品加载，也不弹出额外提示。
学校与分隔线的显隐不改变标题行高度，长名称单行省略并为微信菜单胶囊保留空间。

轻量检查：`node --test tests/mini-program/secondHandHomepage.test.cjs`。开发者工具中
另行检查无学校/有学校、注册及填写学校后返回、退出登录、长校名和搜索交互。
回滚时仅恢复首页的布局和校名读取逻辑；不涉及接口、数据库或注册认证流程变更。

## 发布与编辑草稿

二手发布页按账号保存一个新建草稿及各商品独立的编辑草稿，有效期 7 天，单账号最多保留
最近 20 个条目。只保存表单业务内容、已完成上传的图片 ID、图片类型及提交保护标识，
不缓存预览 URL、加载状态或账号资料。字段修改、图片变化、离开页面时保存；重新进入时
通过现有确认弹窗选择恢复或重新填写。编辑草稿先读取当前商品，原图片只使用当前仍属于
该商品的 ID 与新预览，不恢复已被移除的原图。

临时图片恢复时和提交前通过 [本人图片检查入口](media-assets.md#草稿图片检查与预览刷新)
校验，失效时只移除对应图片并提示重传，文字和其他内容保留；检查失败不清空草稿，暂不
提交。草稿 7 天不延长临时图片 24 小时期限。普通离页保留草稿引用图片，明确重新填写或
移除时释放没有提交保护的临时图片。退出登录清除本人草稿，换号立即清空页面表单，迟到
读取、上传和提交结果不能写入新账号。

提交成功清除对应草稿；失败保留。当前运行期间重新进入同一草稿会等待前次提交结束，
防止先恢复一个随即被成功提交清除的旧草稿。结果不明的图片保护随草稿保存，后续明确
失败也不误释放更早的未确认提交图片。清除使用草稿版本校验，旧提交不能删除新版本。
商品发布和二手订单创建已增加持久化提交标识与服务端结果重放；具体约束、迁移和上线顺序见[创建请求幂等](../database/submission-idempotency.md)。商品编辑仍使用原有草稿和进行中等待机制。

验证使用 `secondHandDraftRecovery.test.cjs`、`secondHandPublishUpload.test.cjs` 和账号隔离
相关测试。未进行真机验收；需人工检查新建、编辑、添加地址返回、退出换号及重传。
依赖本人图片检查入口，发布时 API 在前、小程序在后，无新增数据库迁移。回退页面会
恢复离页丢失内容及临时图片释放行为，不应把无归属缓存迁移到其他账号；原草稿缓存可
保留至失效，不增加额外的全局清理或延长服务端图片期限。

## 商品列表筛选

`GET /api/second-hand/products` 支持组合使用以下首页筛选参数：

- `categoryId`：商品分类 ID；
- `pickupAddressPrefix`：发布商品时保存的自提点前缀，格式为
  `校区 类型 楼栋`；
- `keyword`：商品标题或描述关键词。

自提位置使用商品发布时固化的 `pickup_address_snapshot`，不关联地址簿的当前值。这样卖家
之后修改或删除地址簿记录时，已发布商品仍按当时向买家展示的自提点参与筛选。查询只匹配
完整的 `校区 类型 楼栋`，以及紧随其后的详细地址，避免名称相近的楼栋互相误匹配。

验证时至少覆盖“分类 + 自提位置”组合查询、仅分类查询和不选择自提位置三种情况。若需
回退此能力，可停止传递 `pickupAddressPrefix` 并移除 Mapper 中对应条件，不涉及数据库迁移
或历史数据回滚。

## 商品详情卖家信息

商品新建与编辑共用服务端字段校验：价格大于 0、不超过 99999 元且可精确表示为分；
分类须存在且未删除；标题 2–80 字、描述填写时 4–600 字、自提点填写时 1–500 字；
成色使用小程序现有四个选项，交付及议价开关只接受 0/1，图片提交时须为 1–6 个不重复有效 ID。
编辑保留原有局部更新语义，未传字段保持原值；历史商品不批量改写。
发布和编辑仍执行校园认证、卖家归属、商品状态及媒体归属检查。
验证使用 `SecondHandProductValidationTest`，覆盖新建与编辑同时拒绝非法值，并保留合法局部编辑。
无结构迁移；回退校验会重新允许绕过小程序提交非法商品。

`GET /api/second-hand/products/{id}` 返回 `sellerName`（当前昵称）、`sellerAvatar`
（通过公开头像绑定解析的地址）和 `sellerSoldCount`。成交数按卖家的未删除二手订单统计：
状态 `3`（已完成）及历史线上状态 `9`（转账成功）；其他状态不计入，不使用商品在售状态
或卖家发布数量推断成交。该信息只用于展示，不改变订单或支付流程，无需数据库迁移。

小程序在导航标题与商品图片之间展示头像、昵称，右侧显示“已卖出n笔订单”；数量为 0
或旧接口未返回数量时隐藏该文案。头像缺失时使用统一头像组件的默认用户图标。
验证需覆盖零成交、多笔成交、长昵称和无头像；Mapper 检查统计的卖家、删除及状态条件。
回滚时移除顶部卖家行及新增响应字段、头像解析和统计查询，不修改订单数据。

## 议价与下单的状态联动

同一买家对同一商品发送新报价时，将本人此前待回复（0）的报价转为已有的已失效（3），
保留历史记录、原报价和次数；其他买家以及已拒绝、已撤回、已关联订单的记录不受影响。
小程序点击发送时查询本人待回复与已接受报价；替换旧报价前沿用确认弹窗提示
“发送后，之前的议价将失效”，旧记录仍只显示“已失效”。状态查询失败时阻止发送。
本人已有有效的已接受且未下单报价时，服务端拒绝再次报价，小程序引导按已接受价格下单。
发起报价先锁商品，再锁本人有效报价；旧待回复报价失效和新报价插入在同一事务内完成，
校验失败或保存失败均不取消旧报价。相同金额和相同留言的最新待回复报价重复提交时复用
原记录，不扣新次数、不重复通知；真正的新报价仍按现有次数上限校验。此改动无需结构迁移，
存量多条待回复记录在该买家下一次成功发送新报价时一并失效。回滚代码不能恢复已失效报价。

卖家接受仅将报价从待回复（0）转为已接受（1），不创建订单、不占用商品，也不使其他
报价失效。接受表示同意报价及买家从商品开放的交付方式中选择；买家随后复用商品详情
的交付确认弹层，选择自提或卖家配送及本人地址，并按已接受的报价下单。

`POST /api/second-hand/bargains/{id}/accept` 成功返回空结果，不再返回订单；兼容接收旧
请求体但不使用其中交付参数。`POST /api/second-hand/orders` 携带 `bargainId` 时，服务端
锁商品并锁报价，核对买家、商品、卖家、已接受状态以及不存在任何关联订单，再读取保存
的报价作为订单价格，不接收客户端成交价。无 `bargainId` 的直接下单仍使用商品售价。
配送地址按当前买家的地址 ID 查询、校验归属并生成地址快照，不信任请求中的地址快照。

买家确认创建订单时才占用商品。创建订单的同一事务内将其他待回复（0）和已接受但没有
关联订单（1）的报价转为已失效（3）；成交报价及已有订单的历史报价保留。创建失败整体
回滚，原已接受报价可重试。别人先买走时，本次下单失败。订单取消或商品重新上架不会
恢复其他旧报价；已关联订单的报价即使订单取消或删除，也不能重复下单。

发起议价、接受和拒绝先对商品执行 `SELECT ... FOR UPDATE`，与下单的商品条件更新
使用同一行锁，防止下单完成后插入待处理议价。接受和拒绝只允许在售且无进行中订单的
商品，并使用 `WHERE status = 0` 条件更新，防止过期请求覆盖已接受、已拒绝或已失效记录。
小程序已接受且没有订单的记录显示“待买家下单”，买家可点“去下单”；已有订单的记录
仍进入订单详情。商品详情点击购买也会查找本人已接受且未下单的报价并显示议价价。
指定报价失效或报价查询失败时阻止下单，不静默回退原价。商品标价与分享价格保持原价。
商品详情加载时查询本人有效的已接受且未下单报价，在标价下显示“卖家已接受你的报价 ¥…”并将
按钮显示为“¥… 下单”；首页与收藏列表仍展示公开标价。未登录、非报价本人、不可购买、报价
已关联订单或失效时不显示个人议价提示，查询失败也不保留旧提示；点击下单仍重新查询报价，
创建订单时再次在服务端锁定校验，不能直接以展示价格下单。

接受报价流程本身无需新增数据库字段（拒绝原因的新增字段见下节）。API 和小程序需配套发布，旧客户端仍假定接受返回订单，不能单独
更新 API 后声称旧客户端流程可用。回滚前检查已接受但未下单的记录，不能自动将其变为
订单；历史已有订单不改变交付方式。

历史数据修复见 `docs/database/second-hand-bargain-expiry-repair.sql`。发布时暂停二手交易
写入、备份数据库并保存候选记录后执行：关闭不可购买、下架、已删除或缺失商品的待回复及已接受但未关联订单的报价，以及有后续
订单的未成交旧报价（包括订单已取消或逻辑删除的情况），保留已关联订单和重新上架后新发起的报价。
时间字段精度相同导致同秒报价与订单无法严格排序时，保守关闭该报价，用户可重新议价。
脚本不改变表结构，可重复执行；重跑候选查询应无结果。API列表读取以同样条件返回有效状态，拒绝、接受及议价下单也拒绝有后续订单的旧报价；查询兜底不改写数据库、也不发送历史通知，仍须按发布流程修复历史数据。

验证运行 `SecondHandOfflineTradeServiceTest`、`SecondHandBargainLifecycleTest` 和
`SecondHandBargainMapperXmlTest`；人工检查先议价再直接下单、接受议价、拒绝议价、
取消订单后重新上架。回滚代码不能自动恢复报价；如需回滚数据，应暂停写入后按备份中的
具体 ID 恢复原状态与时间，不能批量将全部已失效报价改回待处理。

## 拒绝议价原因与商品变化失效

拒绝弹窗使用三个互斥选项：“暂时不打算出售”“暂不考虑这个价格”“自定义原因（选填）”。
初始不预选；只有第三项显示原因输入框，最多40个Unicode字符，可留空。选择预设项时不携带
说明；自定义内容不和预设原因拼接。买卖双方记录只展示一条拒绝反馈，原买家报价留言保持独立。
页面只给失效记录保留“已失效”标签，不附加解释句。

`POST /api/second-hand/bargains/{id}/reject` 可接收：

```json
{"reasonCode":"CUSTOM","note":"暂时不方便出售"}
```

`reasonCode` 必须是 `NOT_SELLING_NOW`、`PRICE_NOT_SUITABLE`、`CUSTOM` 之一。
`CUSTOM` 的 `note` 去掉首尾空白，空内容存NULL，超过40字拒绝提交；预设原因忽略 `note`。
状态和原因通过同一条 `WHERE status = 0 AND deleted = 0` 条件更新，不能覆盖已处理或失效状态。
旧客户端无请求体时继续原拒绝流程。列表新增 `rejectReasonCode`、`rejectNote`、`rejectReasonText`
和 `productDeleted`；仅已拒绝记录返回可展示拒绝文本。历史无原因及自定义留空时显示“卖家未填写原因”。
商品已删除或缺失时禁止列表跳转该商品，已有订单入口继续保留。

在商品下架、管理端改为已售出/下架、管理端删除及买家下单的同一事务内，将待回复及已接受
但未关联任何订单的报价持久化为失效；拒绝、撤回和已关联订单记录保留。先锁商品，再锁待失效
报价，确定通知对象后更新状态。下单失败整体回滚，不发送失效通知；重新上架或订单取消不恢复旧报价。

列表返回页面、下拉刷新、操作成功/失败后重新读取。刷新尚未成功时禁用报价操作；刷新失败保留
内容和重试入口，不继续拿旧状态操作。拒绝网络失败保留选项及内容供重试；刷新确认已失效时收起弹窗。
通知带 `tab=issued&bargainId=...` 时补查本人目标记录并展示，即使其不在第一页；后续仍沿用普通角色分页。

### 迁移、验证和回滚

新库结构已更新 `docs/database/second-hand-schema.sql`；现有库先执行
`docs/database/second-hand-bargain-reject-reason.sql`，增加可空 `reject_reason_code varchar(32)`
及 `reject_note varchar(40)`（utf8mb4），不回填虚构原因。再按上述历史修复脚本核对并修复状态，
最后启动依赖新列的API。执行前暂停交易写入、备份数据库和保存修复候选，遵循
`docs/deployment/server-operations.md` 的完整发布必检；开发代码完成不代表生产迁移或模板已验证。

回滚API/小程序时保留新增列及已写入原因，不恢复已失效报价；状态修复按候选ID/旧状态/更新时间
和发布后业务逐条评估，不能用整库旧备份覆盖新增业务。兼容旧客户端无请求体仅针对拒绝接口，
不代表整个历史客户端版本都兼容当前订单接口。

最低检查使用议价生命周期、下单、Mapper、分页、订阅消息和小程序议价逻辑测试；真实MySQL
迁移/并发、弹窗键盘、输入换行、下拉刷新及微信实际送达仍需目标环境/人工验收。

## 买家撤回议价

`POST /api/second-hand/bargains/{id}/withdraw` 沿用登录及校园认证校验，仅报价本人可将
待回复（0）转为已撤回（4）。同一买家重复撤回返回成功；已接受、拒绝或失效的报价
不能撤回。撤回不要求商品仍在售，保留报价、留言、次数与记录，不返还议价次数，
不取消或修改已有订单。已撤回的报价在双方列表保留，并移除操作按钮。

撤回事务只锁议价行，读取最新状态后使用 `WHERE status = 0` 更新，不再申请商品锁。
接受先锁商品、再条件更新议价，不再创建订单；两者竞争同一议价行，最终只能有一个
成功提交。接受成功则撤回提示查看议价记录；撤回成功则卖家不能接受。
接受失败会回滚状态，撤回可以继续。下单引发的报价失效只覆盖待回复及已接受未下单记录，
不会覆盖已撤回记录。管理端修改前同样锁议价行，不能恢复已撤回报价，也不能代买家撤回。

当前没有报价有效期、倒计时或自动过期任务；已失效（3）表示商品变化或下单联动结果。
撤回状态本身使用已有整数列，不需要新增字段；拒绝原因的迁移另见上节。旧客户端不认识状态 4，发布时应
同步更新小程序状态展示和管理端。回滚后不可把已撤回记录批量恢复为待回复；保留状态 4
的展示和拒绝恢复保护，避免旧报价重新被接受。

最低检查覆盖本人/他人权限、重复撤回、终态拒绝、条件更新失败不建单、行锁 SQL，
以及页面成功/失败刷新。单元测试不等于真实 MySQL 双请求并发或事务回滚验证；
小程序弹窗、按钮与刷新交互由用户人工验收。

## 议价记录商品封面

`GET /api/second-hand/bargains/my` 响应补充 `productCoverImage`，从商品当前公开图片绑定中取首张。
同次请求中相同商品只解析一次，缺图返回空字符串；不从客户端逐条请求商品详情，
避免重复请求及误增商品浏览量。无需数据库迁移，旧客户端可忽略新增字段。
小程序收到和发出的议价均展示该封面，缺图使用统一图片组件默认状态，不使用示例图。
验证包括重复商品共用封面、无图、双角色列表与操作按钮；回滚时移除新增字段解析和缩略图，
原有议价、订单和图片绑定不受影响。

## 商品收藏

收藏对象是二手商品，不是已经生成的交易订单。用户可从商品详情收藏或取消收藏，并从个人
中心进入“我的收藏”。卖家不能收藏自己的商品。

- `POST /api/second-hand/products/{id}/favorite`：收藏商品；重复调用保持已收藏，不重复计数。
- `DELETE /api/second-hand/products/{id}/favorite`：取消收藏；重复调用保持未收藏，计数不减为负数。
- `GET /api/second-hand/favorites`：按最近收藏时间获取当前用户的收藏商品。
- `GET /api/second-hand/products/{id}`：响应中的 `favorited` 表示当前用户是否已收藏，
  `favoriteCount` 表示当前有效收藏数。

已售出或已下架的商品仍保留收藏关系并在列表中展示当前状态；逻辑删除的商品不再显示。
收藏关系由 `tb_second_hand_favorite` 的“用户 + 商品”唯一索引防止重复，商品表的
`favorite_count` 在同一事务中同步更新。数据库迁移、校验和回滚见
`docs/database/second-hand-favorite-migration.md`。

### 我的收藏：离页提交取消

为避免误触后商品立即消失，“我的收藏”页的取消操作先仅改变页面内的选择：卡片保留
原位置，按钮从“取消收藏”切换为“收藏”；再次点击即撤销本次取消，不发送重复收藏请求。
当前页头不显示收藏数量；即使全部点了取消，也保留卡片供用户恢复。

详情后返回及切到后台不会提前提交；待取消状态在本次页面实例内保留。商品详情本身的
收藏行为不变，仍直接调用现有接口。小程序被系统强制结束时不保证触发卸载和完成请求，
重新进入时以服务端返回的收藏关系为准，不把尚未提交的选择当作成功结果。

收藏写请求在公共服务中按调用顺序执行；重新进入收藏列表及读取详情前等待已提交的

阻断其他商品，显示中文失败提示；下次进入时失败商品仍按实际收藏状态显示，可再次操作。
已卸载页面不再接收异步列表结果，重叠刷新以最后一次请求为准。

## 当前交易模式

系统配置 `second_hand_trade_mode` 当前必须为 `OFFLINE`。平台只提供商品展示、私信、议价、
下单和交付记录，付款与交付由双方自行协商；平台不代收、不担保、不退款，也不从二手货款
中抽取服务费。

新订单保存 `tradeMode=OFFLINE`，创建后直接进入状态 `1`（待交付），商品进入交易中。卖家
标记交付后进入状态 `2`，买家确认双方已完成商品和款项交接后进入状态 `3`。交付前买卖双方
都可以取消订单，订单进入状态 `4`，商品恢复在售。线下订单不会自动确认完成。

交付方式继续支持买家自提和卖家配送。选择卖家配送时，订单保存买家地址簿 ID 和配送地址
快照；后续修改地址簿不会改变已经下单的配送信息。

订单上的 `payAmount` 和 `sellerIncome` 是为兼容旧数据保留的金额字段；在线下模式中都等于
双方约定价，不表示平台已经收款或结算。`serviceFeeRate` 和 `serviceFee` 固定为 `0`。

旧支付、退款和卖家转账代码继续用于 `tradeMode=ONLINE` 的历史订单善后。当前模式下
`POST /api/second-hand/pay/jsapi/{orderId}` 会拒绝发起新的微信支付。重新开放线上能力前，必须
重新核对微信正式准入、资金关系和接口版本，不能只修改配置值。

买家和卖家订单列表各自返回对方的公开头像 URL（`sellerAvatar` / `buyerAvatar`），
无头像时为空。列表不返回联系电话；只有交易双方通过订单详情，在允许的订单阶段才能取得
`counterpartyPhone`。小程序列表的联系入口据此提供拨打与复制。

### 买卖双方订单列表分组

两端共用 `utils/secondHandStatus.js` 的 `orderStatusGroup`，按订单保存的交易模式分组：

| --- | --- | --- | --- | --- |
| OFFLINE | 1、2、11 | 3 | 4 | 无 |
| ONLINE（含未返回模式的旧订单） | 0、1、2、8、10、11 | 3、9 | 4 | 5、6、7 |

警示样式；历史线上状态 10“收款异常”同样归入进行中。线下不支持的状态与未知状态仅在
全部中展示，不默认归入退款。此规则只影响列表筛选，不改变订单状态、操作权限或资金流程。

轻量验证：`node --test tests/mini-program/secondHandOrderGroups.test.cjs`，覆盖两端所有既有

### 历史服务费配置

`second_hand_service_fee_rate` 仅供历史线上交易兼容，当前管理端隐藏该配置。

- `GET /admin/api/config/second_hand_service_fee_rate`：读取二手交易服务费率。
- `PUT /admin/api/config/second_hand_service_fee_rate`：修改费率，请求字段为

## 订单创建的非空字段约束

`tb_second_hand_order.transfer_attempt` 是 `NOT NULL DEFAULT 0`。如果订单插入语句显式包含
该列，订单实体必须把它初始化为 `0`；显式插入 `NULL` 时数据库默认值不会生效。

订单构造必须初始化 `transferAttempt=0`，Mapper 同时使用 `COALESCE` 防止显式写入空值。
验证必须同时覆盖直接下单和接受议价后买家下单，确保两条路径都可以创建线下订单：

- 使用真实 `NOT NULL` 表结构分别验证直接下单和买家按已接受报价下单，不能只做 Mock 单元测试。

当前接受报价不创建订单，“已接受但无订单”是正常待下单状态。应验证买家携带已接受
报价下单时插入失败会整体回滚，没有遗留商品占用或其他报价失效。

## 私信会话

私信按“商品 + 对方用户”组成一对一会话，买家可从商品详情联系卖家，卖家只能回复已有
互动的买家。消息仍保存商品和可选订单关联，便于交易双方在同一个会话里持续沟通。

- `POST /api/second-hand/messages`：发送私信。
- `GET /api/second-hand/conversations`：按页获取当前用户的会话列表及未读数，详见下文。
- `GET /api/second-hand/conversations/{productId}/{counterpartyId}/messages`：获取一对一消息并
  仅将本次返回、由当前用户接收的消息标记为已读。

旧的 `GET /api/second-hand/products/{id}/messages` 暂时保留兼容，不作为新版小程序的会话入口。

## 联系方式

订单详情仅向订单买卖双方开放。线下订单创建后，详情响应的 `counterpartyPhone` 返回对方
当前手机号；下单前只能使用私信。小程序默认脱敏展示，仅在用户主动拨号时使用完整号码。
历史线上订单仍以支付成功作为开放电话的边界。

## 历史线上订单取消与迟到支付补偿

以下规则仅处理历史 `tradeMode=ONLINE` 订单。当前新建 `OFFLINE` 订单仍不发起平台支付或退款。

- 所有二手履约与资金写入统一按“商品 → 订单 → 支付/退款/转账记录”加锁，与下单、议价的商品优先顺序一致。首次普通读取只定位订单所属商品；取消、交付、确认、管理端处理及支付/退款/转账结果均使用加锁后重读的订单判断状态，不使用旧对象更新。
- 管理员改为取消或退款同样使用上述取消/退款流程，不允许将交付或卖家收款中的订单直接改为自动退款；标记退款成功须有同一订单的已确认成功退款记录，不能仅靠改状态结束资金未决事项。
- 待支付订单先请求微信关单，只有关单成功或重新查单明确为 `CLOSED` 才能按未付款取消并释放商品。关单失败后查到 `SUCCESS` 时校验订单号、币种和金额，保存真实支付流水并进入全额退款；查单失败或 `NOTPAY/USERPAYING/REFUND` 等其他结果不能认定未付款，保留订单，提示重试或等待下一轮核对。
- 已取消订单收到成功支付时仍校验并保存真实流水，随后进入退款，不恢复交易、不重新占用商品。同一订单的支付流水只写一次；不同微信交易号或金额不一致的通知拒绝处理并返回失败。重复支付通知不重建退款单，退款成功后不重新打开订单。
- 订单退款状态及 `REQUESTED` 退款意图在同一事务中落库，提交后才调用微信。退款失败重试复用已有退款单号和原金额，遵循 [微信退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)。请求受理不等于到账；请求超时、`5xx` 或本地结果写入失败时保留意图，先查询原单，仅在微信明确返回 `404 RESOURCE_NOT_EXISTS` 且本地为 `REQUESTED/REQUEST_FAILED` 时补发。
- 退款回调核对订单号、退款单号、币种、原支付金额及全额退款金额。`SUCCESS` 是终态；重复或晚到的 `PROCESSING/ABNORMAL` 不得把成功降级。真实 `ABNORMAL/CLOSED` 保留异常状态供人工处理，定时查询仍可确认后来成功，但不自动更换单号或重复申请。
- 退款成功或确认未付款后的商品释放会排除其他有效订单。已取消旧订单的迟到退款不能解锁新买家的商品。

现有每分钟二手定时任务新增退款核对：每批最多 100 笔，查询距上次更新超过 5 分钟的退款中/异常历史线上订单；历史已取消订单每批最多 100 笔，距上次更新超过 20 分钟时查支付并补偿遗漏成功，失败继续轮转核对。任务受 `app.scheduling.enabled` 控制，不依赖当前交易模式是否为 `OFFLINE`。无需数据库结构迁移；运行开关及存量实际资金状态必须在生产环境核实。

验证覆盖两种取消/支付先后顺序、关单失败与查单不确定、超时旧候选、历史漏回调、重复及冲突交易号、退款意图先提交、退款请求丢响应后查单恢复、异常后的迟到成功、重复退款回调及新订单占用保护。自动化使用模拟微信与数据库映射，不代表生产微信资金验证。回滚应暂停相关订单写入并核对新产生的 `REQUESTED/REQUEST_FAILED` 退款意图，旧版不会补偿这些记录，不能在未处理资金未决订单时直接回退。

### 履约状态与商品一致性

线下取消只允许从待交付进入已取消；已交付订单不能通过普通取消重新上架。
管理端不能把已完成、已取消订单重新改为进行中，也不能从待确认退回待交付。
协商中订单保留商品占用，由管理员明确处理为待确认、已完成或已取消；退款异常同样阻止新订单占用。
历史线上订单的支付、退款和收款结果只能经对应流程确认，管理端不能直接伪造支付或收款成功。

商品编辑、上下架及管理端删除先锁商品后检查订单。存在有效订单时不能直接修改商品状态；
`markTrading` 只允许从占用/交易中写入，`markSold` 只允许从交易中/已售出写入，避免迟到写入把已售商品改回交易中。

超时、自动确认和转账查询列表只作为候选。每笔处理使用独立事务，按上述顺序取得行锁，
重查状态及适用的截止时间；自动确认不处理线下订单。每次事务只处理一个商品，避免批量
持锁与前台请求形成反向等待。转账通知还须与当前转账尝试的商户单号匹配。

本地验证：`mvn "-Dtest=OrderStateConcurrencyMysqlTest,SecondHandOrderConcurrencyTest" -Dorders.mysql=true test`。
真实 InnoDB 测试仅允许连接本机 MySQL，创建并删除独立临时库；覆盖取消/交付竞争、确认/管理端回退竞争、
商品写入失败时订单回滚，以及旧退款不能释放新买家的商品。外部微信调用仍使用模拟，不代表真实资金验证。
无需数据库迁移；回滚代码会恢复并发覆盖风险，回退前应暂停订单写入并核对订单与商品状态，不删除订单证据。

## 历史线上订单的卖家收款

以下内容只适用于 `tradeMode=ONLINE` 的历史订单，不适用于新线下订单。

### 单笔资金来源与模拟开关

历史 ONLINE 退款、确认收货、管理员收款重试及定时收款查询均依据该订单的支付流水，
不再依据全局模拟支付开关跳过真实请求或直接标记收款成功。真实付款必须满足
`RealPaymentGuard` 的来源、成功状态、交易号与金额校验；模拟流水和来源不明的订单拒绝
真实退款、转账，查询任务保留原状态并记录订单 ID 待核对，不伪造到账。
新订单继续使用 OFFLINE；这项修复不重新开放二手线上交易。

存量处理顺序：先只读分类最新未删除支付流水，再逐单核对微信退款/收款结果。
真实且金额一致的订单按原退款号或当前转账单号恢复对账；模拟订单保留测试证据，
缺失、冲突或金额不一致的记录进入人工核对，不补造真实流水。
曾被旧模拟分支标记为收款成功的订单不能仅凭本地状态认定到账，须核对微信结果，
不得批量回退状态或生成新转账单，否则可能重复付款。

以下 SQL 仅返回订单标识、状态与分类，不读取手机、openid 或资金报文；在目标库只读执行。
同一订单有多条未删除支付流水时应另行核对全部记录，不能只凭最新一条确认资金来源。

```sql
SELECT o.id, o.order_number, o.status,
       CASE
         WHEN p.id IS NULL THEN 'MISSING'
         WHEN p.payment_type <> '微信支付' OR p.payment_type IS NULL
           OR p.trade_type <> 'JSAPI' OR p.trade_type IS NULL
           OR LEFT(UPPER(TRIM(p.transaction_id)), 5) = 'MOCK_'
           OR UPPER(p.bank_type) = 'MOCK' OR LEFT(p.payer_openid, 5) = 'MOCK_'
           THEN 'MOCK_OR_UNKNOWN'
         WHEN p.trade_state <> 'SUCCESS' OR p.trade_state IS NULL
           OR p.transaction_id IS NULL OR TRIM(p.transaction_id) = ''
           THEN 'UNCONFIRMED'
         WHEN p.total IS NULL OR o.pay_amount IS NULL
           OR p.total <> o.pay_amount * 100 THEN 'AMOUNT_MISMATCH'
         ELSE 'REAL_CANDIDATE'
       END AS payment_review
FROM tb_second_hand_order o
LEFT JOIN tb_payment_log p ON p.id = (
  SELECT MAX(p2.id) FROM tb_payment_log p2
  WHERE p2.order_number = o.order_number AND p2.deleted = 0
)
WHERE o.trade_mode = 'ONLINE';

SELECT order_number, COUNT(*) AS active_payment_count
FROM tb_payment_log WHERE deleted = 0
GROUP BY order_number HAVING COUNT(*) > 1;
```

无数据库迁移或历史数据改写。回滚旧代码会恢复模拟开关误报成功风险，回退前应暂停历史
ONLINE 收款操作并逐单保留支付、退款和转账证据。单元测试覆盖真实创建/查询、模拟拦截及

### 回调持久化与重试

二手支付、退款和转账回调移除了进程内全局锁，使用现有商品→订单→资金记录的数据库行锁，
同一订单串行处理，不同订单不再竞争全局通知锁。处理成功后，支付流水、退款结果或转账状态
随事务提交；控制器在服务事务返回后才回应 HTTP 200。锁等待超时、写入失败或找不到本地记录
时返回 HTTP 500，由通知方重试。事务显式回滚异常，不能在未落库时确认接收成功。
本实现同步完成持久化，不新增内存队列或独立通知收件箱。

重复支付只保存同一微信交易号的一份流水，冲突交易号报错；退款成功不被重复通知回退，
转账通知必须匹配当前尝试单号，终态重复通知不重复改变订单。既有退款持久化意图和定时查询
继续承担取消后的补偿。测试覆盖取消与支付竞争、重复通知、缺失记录重试、跨实例同单等待
和不同订单独立处理；数据库和微信端的生产联调不能由这些模拟测试替代。

买家确认收货后，订单进入收款处理中。后端使用独立 `transfer_out_bill_no` 发起微信商家
转账，并保存微信状态、转账单号和确认收款参数。结果不确定时保留处理中，由定时任务查询，
不会直接判定为失败。

当微信返回 `WAIT_USER_CONFIRM` 时，卖家调用
`GET /api/second-hand/orders/{id}/transfer-claim` 获取 `mchId`、`appId` 和 `packageInfo`，
再由小程序调用 `wx.requestMerchantTransfer`。小程序成功拉起页面只表示确认页已打开，最终
到账以微信回调或后端查询到 `SUCCESS` 为准。

管理员对收款中订单执行“同步收款状态”，只查询当前转账；对收款失败订单执行“重新发起
收款”才会生成新的商户单号，避免重复付款。

### 当前实现缺口与历史订单处理

当前仓库 `SecondHandServiceImpl.transferToSeller` 对所有非 200/204 创建响应均写入 `QUERY_REQUIRED`，包括确定性的 4xx；`querySellerTransfer` 遇到非 200（包括 404）仅记录失败并返回，尚无自动退出或有上限的重试机制。这是当前代码缺口，不能把拟议的错误分类写成已实现行为，也不能仅凭仓库判断生产是否运行此版本。

历史收款中订单须逐单核对微信侧是否生成转账单、当前结果及本地商户单号。无法确认是否受理时不得直接生成新单重付；确认未创建后，仍须先明确处理方案、场景准入和版本，再进行失败标记或管理员重试。当前缺口不影响新 OFFLINE 订单，不能为恢复历史订单将新交易切回线上。

未来修复应区分确定性拒绝与未知网络结果，并覆盖创建失败、404、WAIT_USER_CONFIRM、原单查询及重试不重复付款；本次文档整理没有实现该修复。

## 商品首页分页

`GET /api/second-hand/products` 接受 `page`、`pageSize`：默认第 1 页、每页 20 条，每页范围 1–50；页码必须为正整数。非法参数返回面向用户的业务错误，不执行商品查询。响应仍是原有商品数组，排序为 `create_time DESC, id DESC`，学校、分类、关键字等筛选保持不变。分页在 SQL 内执行，再批量解析当前页公开图片。页偏移使用 long，避免整数乘法溢出。

`GET /admin/api/second-hand/orders` 支持 `page/pageSize/status`，默认第 1 页、20 条，上限 50；`status` 可为 0–11，留空读取全部。排除逻辑删除订单，状态在分页前过滤，按创建时间与编号降序稳定排序。仍可管理历史线上和线下订单，详情、状态操作与收款重试入口保持。

响应 `data` 从数组改为 `{total, page, pageSize, list, abnormalOrders, turnover}`。完整筛选范围内，异常数仍统计状态 7/10/11，金额仍累加状态 3/8/9/10 的 `payAmount`（空值按零），保留原管理页计算口径，不将该汇总表述为实际到账。汇总不下载订单明细或图片；分页与汇总共用状态/删除过滤片段。当前页商品图片批量解析，支付期限配置在存在历史线上待付款订单时每页只读取一次。旧内部管理订单 Mapper 加默认 20 条上限，当前管理入口使用分页查询。

管理表格使用服务器总数，翻页沿用已提交状态筛选，新状态或页大小变化重置第一页。刷新与操作后保留原页，当前页已无记录时最多补读一次剩余末页；失败保留原订单、分页和统计，账号、请求版本或卸载改变后丢弃旧响应。API 与管理端须协调发布。完成静态类型、生成 SQL、模拟服务/控制器及提取页面逻辑检查，未执行真实 MySQL、生产发布、资金链路或浏览器验收。


## 管理端议价与留言分页

`GET /admin/api/second-hand/bargains` 支持 `page/pageSize`，默认第 1 页、20 条，上限 50，返回 `{total, page, pageSize, list, pendingBargains}`。待回复数量仍统计完整原查询结果中状态为 0 的议价记录，不从本页推算。保留原商品、买卖双方及未删除关联订单的左连接范围，历史同一报价对应多个订单时保留关联行，按议价创建时间、议价编号、订单编号降序稳定排序；表格使用议价编号和订单编号共同识别行，状态操作仍针对报价编号。列表和汇总共用原关联/删除条件，不修改议价处理规则。

`GET /admin/api/second-hand/messages` 支持 `page/pageSize/productId`，返回 `{total, page, pageSize, list}`，分页限制同上。商品编号留空查全部、非空必须为正数；商品和逻辑删除过滤在分页前执行，与总数共用条件。按留言创建时间和编号降序排列，保留内容及双方展示，不改变用户会话授权或阅读标记。

## 用户会话列表分页

`GET /api/second-hand/conversations` 接受 `page/pageSize`，默认第 1 页、20 条，每页范围 1–50，响应仍为会话数组。按“商品 + 对方用户”取最近一条未删除消息，再按消息时间和编号降序分页；仅查询已认证的当前账号参与的会话。当前页每个会话的未读数覆盖该会话全部未读消息，不是本页消息数。最近消息没有订单关联时，保留最近一条有订单关联的历史消息作为回退。

分页及会话汇总由同次 SQL 完成，不把全部消息历史下载到服务层聚合。整页核对调用账号、商品与对方编号后，批量解析当前页未删除商品的公开图片；内部账号证明和媒体商品编号不序列化。已删除或缺失商品不解析封面，商品标题、对方名称缺失时沿用“商品”“同学”回退。发送私信后只按新消息编号及当前发送者读取单条结果，不再读取商品全部消息。

小程序会话列表原布局保留，原生触底续页；刷新从第一页读取，失败保留记录及页码，重叠会话去重，重复请求合并。账号或会话改变时清空旧记录并重新加载；隐藏、卸载及迟到响应不能写回当前列表。旧客户端无分页参数只获取首屏，API 与小程序须协调更新。

完成生成 MyBatis SQL、模拟服务和客户端逻辑检查；未执行真实 MySQL、查询计划、生产发布或界面验收。会话内消息及旧商品消息入口的后续整改见下一节；限流仍未实施。

## 会话消息历史与增量读取

上述会话消息接口及旧商品消息接口接受 `pageSize`（默认 20，范围 1–50）和互斥的 `beforeId`、`afterId` 正整数游标，响应仍为数组。无游标取最近一页，`beforeId` 取更早的一页，`afterId` 从游标后取紧邻的新增一页，避免直接跳到最近消息而漏掉积压。所有响应均按 `create_time, id` 升序展示；SQL 以时间及编号组合定位，同秒用编号区分，历史空时间排列在最前。游标必须属于当前账号、当前商品和指定双方；已逻辑删除的游标仍可定位，但其内容不会返回。消息时间不可在分页过程中改写，本方案不提供数据库快照。

会话读取保留校园认证、有效商品及卖家/买家互动校验。查询行均限定当前账号及指定双方，整页身份核对后只为返回的未读接收消息更新 `read_time`，更新再校验当前接收者和未删除状态，未加载历史和查询后到达的新消息不被标成已读。完整会话未读数及任务统计仍由原汇总查询计算。旧商品消息入口保留当前账号参与范围、不要求当前商品仍有效、不改阅读标记；允许跨该商品的多个对方翻页。原无调用方的内部全量方法加 20 条上限，正式入口使用可持续翻页的新方法。

小程序沿用原会话布局，首屏最近 20 条，滚动到顶部读取旧记录并定位原首条消息；15 秒轮询仅读取新增消息，后续轮询继续消化超过一页的积压。旧历史、轮询与发送结果按编号去重并保持时间顺序；失败不推进游标。发送只合并返回的单条结果，不能用该编号推进读取游标，否则会跨过未加载消息。页面展示/手动刷新重新取得最新首屏和联系方式，轮询不重查商品、用户或订单详情。账号或会话变化立即清理消息、电话及输入；隐藏/卸载、过期请求和迟到发送不写回，不触发旧账号订阅请求。

API 与小程序须协调更新：旧客户端无游标只能取得最近首屏，不能继续视作完整历史；新客户端可从返回数组首/尾消息取游标。回退消息实现应同时回退客户端，保留消息和已读记录。本次无数据库迁移；上线前仍需核对真实索引及执行计划、管理员删除游标后的翻页、历史空时间与多页未读，并人工验收上滑定位、发送和切换账号。未执行真实 MySQL、生产发布或真机验收。

## 异常订单求助核验（2026-10-11）

当前 `ORDER_DISPUTE=11` 表示管理员可按状态转换规则标记协商中，不代表用户已提交申诉；没有申诉受理、独立证据、处理记录或处理进度接口。私信不是平台求助队列，管理员修改状态或 `cancelReason` 也不等于回复用户。

线下订单没有平台退款/收款。管理端可按既有状态边界从待交付或待确认进入协商中，再从协商中转待确认、完成或取消；这些操作不处理线下实际资金。历史线上订单的协商状态仅允许从待交付/待确认进入，再返回待确认，退款和收款继续经过真实流水校验，不允许直接改成资金成功。历史线上退款异常 `7`、收款失败 `10` 的资金处理能力仍按既有流程执行，不能靠协商状态替代。

本批仅将历史线上买家取消失败提示由“请发起申诉”改为“当前订单无法取消，请先与卖家协商”，避免引导到不存在的申诉入口；权限、状态、金额和资金操作未改变。该提示不表示平台已经受理问题。按用户要求跳过全部前端页面相关实施，不新增配套求助接口、表或证据用途；产品待确认项集中见 [跑腿订单求助核验](../mini-program/order-flow.md#异常订单求助核验2026-10-11)。本项仍未完成完整用户求助闭环。
