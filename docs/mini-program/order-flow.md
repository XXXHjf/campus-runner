# 跑腿订单与资金流程

本页描述当前代码中的跑腿订单，二手交易使用独立订单模型，见 [二手交易](../api/second-hand.md)。状态以 `OrderStatusConstant`、`OrderServiceImpl`、`TakeOrderServiceImpl` 和支付/转账服务为准；服务端响应字段以当前 DTO/VO 核对。`tb_orders` 的早期建表快照不是当前结构。

## 角色与金额

### 2026-10-11 第二批接单与额度整改

用户已确认正式接单和额度建议；本节是当前本地实现，业务 JAR 尚未发布。没有本批前端页面改动，不引入生产测试接单例外。

`TakeOrderServiceImpl.take` 先锁订单，在待接单校验后拒绝发单人本人接单；再锁接单人的身份行，要求未删除、有效校园认证及有效学校。双方不可变地址快照的 PICKUP/RECEIVE 两个角色都必须匹配接单人学校，缺失或冲突拒绝直接按 ID 接单。查询不使用发单人当前学校或可变地址簿替代订单证据；身份锁防止判断期间认证/学校被同时修改。既有行锁与受影响行数检查保留，失败不写接单记录、不发送成功通知。模拟支付开关也不会绕过接单限制；测试使用隔离环境和不同测试账号。

预览及有偿创建共用 `OrderAmountServiceImpl.calculate`：普通/代买应收（跑腿费加商品金额）都不能超过 `runner_transfer_single_max`；代买继续要求含服务费的实付不超过该额度，普通实付可因服务费超过应收额度。无偿普通单仍不发起微信付款。本批不改 UI 或普通服务费规则。

预览/创建、付款前及收款统一使用 `RunnerAmountPolicy.transferMax`，缺配置保持已有默认 200 元；已存在但空白、非法、零/负数、无法精确到分或超过整型分值范围的配置均拒绝，不向下舍入额度。200.000 可精确到分，200.001 不能。真实 `jsapiPay` 和模拟付款均在写入成功或调用支付方前核对存量应收、服务费和实付的关系及当前额度，绝不按新费率重算旧单。真实收款仍核对参与人、订单状态及真实支付流水。

生产只读核验：MySQL 5.5.36，当前配置额度 200.00 元、服务费率和最低服务费均为 0；这是系统配置，不证明微信商户获批能力。历史自接单记录共 18 条，按订单状态 1/2/3/5/6 分别为 5/2/2/4/5。与接单人当前学校比较的快照缺失/冲突聚合未发现记录，不能据此证明历史学校从未变化。快照 SUBMIT 2 条、LEGACY_CURRENT 158 条，旧回填仅为当前来源记录，不能当作提交时原始证据。汇总中当前在途应收未超 200 元，未逐单核对真实资金流水；没有修改或自动取消历史单。

降低额度前先盘点未结清订单及商户能力，当前代码不会自动阻止管理配置下降。旧未支付单超出新额度则停止新付款，保留订单并提示调整重下；已有预支付会话可能在配置变化后完成，不能承诺付款前检查能撤回已签发的微信会话。已支付未接单单可按既有取消退款流程人工评估，已承接/完成单按实际状态与支付、退款、转账流水核对；不得自动改价、拆分或部分转账、伪造成功。额度变化不能保证历史承诺在当前微信能力下可执行。

发布无需本批新增表，但依赖既有订单地址快照结构，上线前仍需核实已有迁移与备份。回滚保留历史记录、快照和流水，不能批量清异常或改已支付金额；撤销新规则会重新开放本人/跨校接单及超额发布，必须另行确认。最低检查覆盖接单身份/角色/学校边界、金额精度/配置变化、付款方调用及模拟隔离；真实资金与并发数据库验收不能由 Mock 测试替代。

同一个用户可在不同订单里担任发单人或接单人。私有订单详情与写操作需要登录；完整详情和凭证仅发单人或有效接单人可读，非参与人只能读取待接单订单的公开投影，隐藏规则见下文。游客仅可读取脱敏的公开预览，见 [订单接口](api-orders.md)。

普通有偿单的发单人实付为跑腿报酬 `price` 加服务费 `serviceFee`。代买单另有商品金额 `productAmount`：发单人实付为商品金额、跑腿报酬和服务费之和；接单人应收为商品金额加跑腿报酬。服务端根据分类稳定编码及系统配置重新计算金额，不能信任客户端传来的金额快照。代买实付和应收共用 `runner_transfer_single_max` 上限；转账申请还独立校验单笔额度。普通及代买的金额预览/创建都校验应收上限，付款前复核当前额度；代买还校验实付上限。无偿普通单不发起微信支付。

管理端维护 `service_fee_rate`、`service_fee_min`、`runner_transfer_single_max`，路径见 [管理端接口](../api/admin-management.md)。发布前可调用 `POST /api/order/amount-preview` 显示服务端计算结果。

支付、退款、转账和流水中的元转分统一通过 `PaymentAmount` 使用 `BigDecimal.movePointRight(2).intValueExact()`，不经过浮点数、不截断或舍入。支付金额必须为正数，服务费可为零；不足一分的有效小数及超过整数分上限（21474836.47 元）的金额均拒绝，此上限不替代业务金额限制。普通单不足一分的报酬不能按免费单提交。支付成功回调、主动同步和超时查单（包括关单失败后的复查）在更新状态前核对订单号、成功状态、`amount.currency=CNY` 及 `amount.total` 与订单实付一致；总额缺失不能用订单金额补齐，优惠后的 `payer_total` 不作为订单总额。金额不一致时保留原状态，须核对支付结果后再处理。

本地验证使用 `PaymentAmountTest`、`PaymentAmountServiceTest` 与支付/退款相关单元测试，覆盖 0.29、0.57、1.13 元和转换边界；真实扣款及回调仍需微信环境验证。无数据库迁移；回滚代码会恢复截断和漏检风险，回退前应暂停相关资金操作并核对受影响流水。

发布页采用单页填写、订单核对后提交。跑腿类型从当前可发布分类接口读取；选中代买时显示商品金额并要求有偿，普通类型可选择免费或有偿。有偿订单在核对时使用服务端金额预览，创建订单后再发起微信支付；有偿订单支付未完成不能提示发布成功。

## 并发状态更新

接单、取消、派送、送达和发布人确认先锁 `tb_orders` 主订单；需要更新接单记录时，再锁
`tb_take_orders` 并重新读取状态。主订单与接单记录必须处于匹配的履约阶段，才能向下一阶段更新，
两次写入在同一事务中完成且均须影响一行。取消与接单竞争时，只允许先取得主订单锁的一方成功。
重复送达不会覆盖确认或收款后的状态，已送达记录不能退回派送中。

按订单号更新支付、退款和收款状态还带旧状态条件：迟到支付只能更新未支付订单；
退款结果只能推进可退款状态；已收款成功不能被迟到的失败结果覆盖。
这些保护同样覆盖定时核对和开发模拟入口，不能通过通用状态写入任意切换履约阶段。

验证使用 `OrderStateConcurrencyMysqlTest`（`-Dorders.mysql=true`）在独立本机临时库中制造真实锁等待，
覆盖取消/接单两个先后顺序、派送/送达竞争及确认后重复送达；
`TakeOrderLifecycleTest`、`OrderConfirmationStateTest` 验证旧状态和越级请求拒绝。
无需数据库迁移或前端修改；回滚前应暂停履约写入并核对主订单与接单记录，不删除业务数据。

## 预期送达时间

新版发布页提交 `expectedDeliveryTime`（`yyyy-MM-dd HH:mm:ss`，与现有接口采用相同本地时区，当前业务为香港/北京时间）。它表示用户选择的具体日期和时分，服务端校验必须晚于创建时刻并按分钟保存，确认弹窗停留、授权等待和请求延迟都不改变该时刻。列表和双方详情直接显示此时间，倒计时使用同一截止时间，不再通过 `gap` 反推。

### 发布前服务端校验

`POST /api/order` 在创建订单前独立校验以下规则，不能依赖小程序拦截：

- 当前用户必须存在且未删除，注册资料完整（头像、有效昵称、有效手机号），校园认证通过且已绑定学校。资料完整度复用 `UserService.getCurrentUser()` 的判定，见 [用户登录与校园认证](../api/user-onboarding.md)。
- 取件、送达地址必须是发布人本人未删除的地址，且与认证学校一致。学校、校区、地点类型、楼栋均须未删除，学校及各层级关联必须一致；历史错误地址也拒绝使用。
- 联系人允许另行填写，去除首尾空白后须为 1–50 字，手机号须符合 `1[3-9][0-9]{9}`。门禁仅接受 `0/1`，跑腿分类必须存在且启用。
- 自动取消时间缺省为提交时刻加 24 小时，显式提交时必须在未来；它不要求早于预期送达时间。固定送达时间按分钟截断后须在未来，且剩余分钟可存入整数 `gap`，避免超范围转换；旧客户端仍可仅提交正整数 `gap`。
- 金额快照由服务端重算；跑腿费不得为负数或超过两位小数，非代购订单不能携带非零商品金额。无偿普通订单保留现有规则，代购和付费订单沿用金额计算校验。

该校验无需数据库迁移。验证使用发布服务的非法请求测试、用户资料测试与地址映射解析检查；发布日志仅记录用户 ID。回滚发布校验会重新开放这些非法请求，应保留此校验并修正历史账号或地址资料。

`gap` 仅保留为创建时到截止时间的向上取整分钟快照，兼容旧客户端及既有时长逻辑；服务端忽略新版客户端传入的 `gap` 并重新计算。旧客户端仍可仅提交正整数 `gap`。旧订单的 `expectedDeliveryTime` 保持空值，列表和详情沿用原来的创建时间加 `gap`、向上进位到整分钟的显示；详情倒计时同步此兼容显示。不能从旧数据可靠恢复最初选中的时刻。

`deliveryTime` 是实际送达记录，不能复用为预期时间。数据库增量迁移见 [预期送达时间迁移](../database/runner-expected-delivery-time.sql)：生产先备份 `tb_orders`，新增可空列，再部署 API，最后发布小程序；不回填历史订单。回滚先恢复客户端和 API，保留新增列及已保存的时间即可，不删除订单和资金流水。迁移脚本只执行一次；执行后通过 `SHOW COLUMNS FROM tb_orders LIKE 'expected_delivery_time'` 检查列类型和空值支持。上线验证需覆盖确认停留超过一分钟、跨日选择、过期提交、新旧客户端及已有订单查询。

新订单创建时将 `exceedTime` 同步为选定截止时间，兼容管理端现有“最晚送达”展示；接单继续使用同一时间，不会延后截止；已经到期的新版订单拒绝接单。旧订单保留接单时间加 `gap` 的历史截止记录。旧的超时降价定时任务、指数降价公式、专用查询和 `realPrice` 运行时代码已删除；超时不自动降低报酬或改变实付、收款金额。数据库 `real_price` 列保留历史数据，不执行删除或回填。未来如引入违约或扣费，必须重新设计独立规则和资金流水。

## 订单状态

| 状态 | 含义 |
| --- | --- |
| `-4`、`-3`、`-2` | 退款异常、退款成功、退款中 |
| `-1` | 未支付 |
| `0` | 待接单 |
| `1`、`2`、`3` | 已接单、配送中、已送达；代买的 `1` 在界面显示“待购买” |
| `4` | 已取消 |
| `5` | 发单人确认收货 |
| `6`、`7` | 接单人收款成功、收款失败 |

普通路径：创建订单后，有偿单先进入 `-1`，支付成功后进入 `0`；无偿单直接进入 `0`。接单、配送、送达、发单人确认依次为 `0 → 1 → 2 → 3 → 5`。有偿单之后按转账结果进入 `6` 或 `7`。代买从 `1` 进入 `2` 前须提交购买凭证，确认完成后商品金额与跑腿报酬合为一笔接单人转账。状态 `3` 仅代表送达，不能当作发单人确认完成。

无偿普通单的新记录金额为 `0`，历史记录可能为空；双方详情和接单列表仍显示零元。无偿单在 `5` 即已完成，归入接单列表“已完成”，不显示收款操作或付费明细，不能为消除待收款显示而改成 `6`（收款成功）。收款入口按实际应收判断：普通单为跑腿费，代买为商品金额加跑腿费；真实及模拟收款均拒绝应收为零的订单，提现核对任务不筛选这类订单。此修复无需迁移或回填；验证应覆盖零元、历史空金额、正常付费及代买垫付款。回滚保留订单状态和流水，旧版界面会重新误显示待收款入口。

## 操作与异常

### 异常订单求助核验（2026-10-11）

本批按用户要求跳过所有前端页面相关实施。当前没有订单求助提交、证据绑定、处理队列或用户查看处理进度的服务端链路；订单说明、送达/购买凭证及取消原因是既有业务材料，不能替代求助工单。定时资金核对与订阅通知也不能证明有人接收并处理用户问题。

| 场景 | 现有处理能力 | 仍缺少的闭环 |
| --- | --- | --- |
| 已接单后履约争议、未送达或待确认 | 双方履约/确认入口；管理端查看订单及凭证 | 问题提交、接收人、协商记录、处理结果反馈；不能擅自开放取消/退款 |
| 退款异常 `-4` 或退款未决 `-2` | 管理端按原退款号核对/重试，定时核对；微信确认异常须商户平台处理 | 用户补证、人工受理和处理进度；申请受理不等于到账 |
| 收款失败 `7` 或待收款 `5` | 实际接单人收款申请及资金核对 | 人工受理和结果说明；不能根据求助直接补发或改成成功 |
| 支付状态/金额不一致 | 拒绝继续资金操作并保留原流水 | 核对真实流水并联系用户的负责人和反馈记录 |

管理端取消/退款复用 `OrderCancellationService`，仍受现有状态与真实支付校验限制；本批不扩大资金操作权限。二手异常状态及历史线上/线下边界见 [二手求助核验](../api/second-hand.md#异常订单求助核验2026-10-11)。

以后恢复此需求时，待确认的最小方案是：仅订单参与人提交说明及私有证据；指定管理员队列受理；独立记录待处理/处理中/已反馈及处理人、时间和回复；参与人能查看反馈。工单不能自动改变订单、退款或收款状态。处理负责人、覆盖的订单类型/状态、回复时限、结案和重新提交规则、证据保留期仍需确认，再设计页面及配套服务端数据结构。本批未新增工单接口或迁移，不把现有后台操作标为求助闭环完成。

跑腿支付申请只允许发单人操作；订单 ID 存在且待支付不能代替归属校验。履约更新先锁主订单，再锁定并重新读取接单记录，核对双方状态一致，只有已接单转配送中、配送中转已送达可以前进。重复已完成的履约请求不倒退主订单，取消、退款及收款终态不接受旧履约记录继续推进。确认收货也锁定主订单后检查已送达状态，避免并发重复确认覆盖后续收款状态。验证使用 `PaymentAmountServiceTest`、`TakeOrderLifecycleTest`、`OrderConfirmationStateTest` 和订阅通知测试；无结构迁移。

接单仍在事务中先锁主订单，再锁接单人身份并校验学校、时限，然后更新订单和插入接单记录。
小程序不通过接单联系人资料接口判断能否接单：该接口仅允许订单参与者读取，不能作为未接单用户的前置检查。
接单接口的数据库或事务异常在原事务结束后，由独立只读事务重新查询订单及有效接单记录。
仅订单处于接单后的状态、记录有效且接单人确为其他账号时，提示“该订单已被接单，请选择其他订单”；
仍待接单、记录不能证明他人接单或重新查询失败时提示“接单暂未成功，请刷新后重试”。取消、订单不存在、
认证、学校及自己发单等业务限制保持具体提示，不把未支付或退款状态误报为已被接单。
异常日志仅记录订单 ID、异常类型及 SQLState／数据库错误码，用于区分死锁、锁等待及其他故障，不记录 SQL 或原始异常正文。
不自动重试接单写入；未知网络结果不推断他人接单。验证使用 `TakeOrderFailureFeedbackTest`、
`TakeOrderBoundaryTest` 和 `tests/mini-program/takeOrderFailure.test.cjs`；真实 MySQL 并发与真机提示另行验收。

### 跑腿／代买完成后的收款提醒

发单人首次确认完成（主订单 `3 → 5`）并提交事务后，向该订单有效且已送达接单记录的用户发送订阅通知。

## 取消、关单与退款规则

| 场景 | 处理 |
| --- | --- |
| 无偿待接单订单 | 直接进入 `4`，不请求微信退款 |
| 本地未支付的有偿订单 | 查询微信；确认未支付后关单，关单成功或查到已关闭才进入 `4` |
| 取消时已支付，或付款抢先于关单成功 | 按 `payAmount` 全额退款，包括跑腿报酬、商品金额及服务费，进入 `-2` |
| 查单/关单失败，支付状态未知 | 保持原状态，返回可重试提示，不把未知状态当作未支付 |
| 已接单、履约中、确认完成、收款成功或失败 | 不开放取消或独立退款，须先协商履约与骑手款项，防止退用户同时向骑手付款 |
| 历史已取消、有实付金额但漏退 | 管理员通过退款入口查询微信，仅确认 `SUCCESS` 且未见已有退款后补退；微信显示 `REFUND` 时应先核对退款流水，不能再次发起；不能仅凭正数金额判定已付款 |
| 模拟支付订单 | 拒绝真实微信退款，不将模拟结果当作资金退回 |

接单、取消、支付同步/回调及退款状态更新锁定同一订单行。取消的状态与退款记录先在同一事务中保存并提交，再请求微信，防止外部已受理而本地因异常丢失退款单。初始退款记录标记 `REQUESTED`（本地申请已受理，微信结果待确认），微信返回 `PROCESSING` 后才显示退款中；以整数分精确换算金额。已有退款记录复用原退款号和金额，不因重试生成新单。[微信退款说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791862)要求失败重试使用原商户退款单号。

退款申请响应、回调和定时查询统一更新退款记录及订单：`SUCCESS → -3`，`PROCESSING → -2`，申请被拒绝/退款异常/关闭 `→ -4`。请求超时、5xx 或查单失败保留未决记录，不宣称退款成功；已成功或微信已确认异常的退款不会被迟到的处理中/申请失败响应覆盖。申请被拒绝在本地记录为 `REQUEST_FAILED`，可复用原号手动重试；微信确认 `ABNORMAL/CLOSED` 时不自动重建退款单，管理员应在微信商户平台处理。微信已受理的退款重复操作只查询原退款单，不再次申请。

退款申请被明确拒绝时，`content_return` 保存 HTTP 状态及微信 `code/message`，用于管理员核对原因；不直接把微信原始消息展示给用户，也不将响应正文写入日志。HTTP 429 限流和 5xx 属于结果未决，不能认定申请失败；人工重试遇到这些响应时恢复为待核对状态，继续复用原退款号查询或补发。[微信退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)要求限流或系统异常时原单原参数重试。

当微信返回 `403 / NOT_ENOUGH` 且提示“基本账户余额不足”时，是商户可用退款资金不足，已确认用户支付成功也不能保证退款可受理。先在微信商户平台核对并补足基本账户可用余额，再通过管理端原号重试；不得直接改为退款成功。具体账户要求以该笔微信响应为准，不能将支付成功、结算余额或模拟流水视为可用退款资金。

退款核对任务每分钟运行一次，默认核对 `updateTime` 超过 20 分钟的 `REQUESTED/PROCESSING/REQUEST_FAILED` 跑腿退款记录。微信查不到 `REQUESTED/PROCESSING` 退款单（404）时，使用已保存的退款号补发，覆盖保存意图后进程中断的情况；`REQUEST_FAILED` 不自动补发，其他查询失败留待后续核对，一笔失败不阻断其他订单。历史已取消订单收到迟到支付成功回调时保存退款意图，交给此任务核对/补发。任务依赖 `app.scheduling.enabled` 开启。当前二手交易使用独立流程，此任务按跑腿订单关联筛选。

管理端按服务端 `code=1` 判断业务成功，`code=0` 显示失败原因；取消和退款接口返回最新订单及退款状态，分别提示申请已受理、退款中、微信确认成功或失败。列表、详情展示最新退款记录；同一页面提交中禁用重复操作，微信已受理或异常的单不开放再次申请，`REQUEST_FAILED` 可人工复用原号重试。接口错误时刷新列表，避免继续显示已经发生变化的旧状态。

### 模拟支付与真实资金隔离

真实退款、跑腿收款及二手存量线上订单退款/收款入口统一验证支付流水：订单号一致、来源为微信 JSAPI 支付、交易状态为 `SUCCESS`、微信支付单号非空、没有模拟标记、未逻辑删除，支付总额须以整数分精确匹配订单应付金额。缺失流水或来源无法确认时拒绝真实资金请求；关闭模拟开关不会使历史模拟流水变成真实支付。

退款创建与重试同时核对原支付总额和退款金额，退款金额必须大于零且不超过原支付；已有退款记录不绕过检查。转账须同时匹配订单应收金额、支付总额减服务费及服务费快照，不接受截断小数或超额转账。二手卖家收款校验失败记录为失败且不请求微信，退款校验失败不创建退款流水。

本次复用现有流水字段，无数据库迁移。针对性测试 `RealPaymentIsolationTest`、`WeChatTransferSubmissionTest`、`WeChatRefundSubmissionTest`、`RefundLifecycleTest` 验证模拟/未知来源、缺失流水、失败状态、金额异常的拦截及真实支付正常路径；测试使用模拟客户端，不验证真实资金到账。历史异常订单需逐单核对微信支付记录，不得通过修改模拟标记绕过校验。发布和回滚遵循生产操作文档；回滚到旧版本会恢复资金隔离漏洞，紧急回退时应停用真实退款和转账入口，并继续核对已受理的真实资金流水。

### 跑腿收款权限

`POST /api/wx-transfer/transfer/{orderId}` 在服务层读取订单的有效接单记录，只有记录中的实际接单人可以申请收款（包含失败重试）。接单记录须关联当前订单、未删除且已送达；未登录、发单人、其他用户以及缺失/取消的接单记录均不能触发真实转账。收款微信账号根据接单记录的 `userId` 查询，不能由调用者身份或请求参数指定；账号缺失或 OpenID 为空时拒绝转账。

此校验先于支付流水查询和微信请求，继续保留真实支付来源与金额校验。`WeChatTransferAuthorizationTest` 覆盖越权、异常接单记录及收款账号缺失；`WeChatTransferSubmissionTest` 验证实际接单人的正常申请和失败重试，以及请求中的收款 OpenID。无数据库迁移；回退该修复前应停用收款申请入口，避免恢复越权转账风险。

### 收款流水和通知可靠性

跑腿转账申请获微信受理后即保存应收金额、收款人和返回状态，不能等最终回调才建立流水，否则丢失回调时定时核对会跳过该订单。申请结果和重复通知在锁定主订单后更新同一流水；已成功记录不被迟到的待确认响应覆盖。跑腿回调的订单状态与流水在同一事务提交。微信查询的 `FAIL/CANCELLED` 更新为收款失败并保存结果；单笔查询异常不阻断同批其他订单。不据此补发新订单号或宣称资金已到账。

跑腿转账及二手支付、退款、转账回调遇到本地锁占用时抛出异常，由通知控制器返回失败，不能跳过业务处理却返回成功；[微信商家转账通知规范](https://pay.wechatpay.cn/doc/v3/merchant/4012712115)以 HTTP 200/204 作为成功应答。成功重复通知继续按原幂等逻辑处理。支付和转账的请求准备、成功响应及解密通知日志已收敛，不应输出完整参数或通知内容。

当前日志仍有缺口：`WeChatTransferServiceImpl` 的申请失败、撤销和查询失败分支仍记录微信响应正文；`SecondHandServiceImpl` 的收款异常仍记录完整异常。不能据上述收敛断言所有支付日志都只含摘要。日志安全约束仍以根目录 `AGENTS.md` 为准，后续修改这些入口时须一并核对；本轮没有修改日志代码。

验证使用 `CallbackContentionTest`、`TransferLogLifecycleTest`、`TransferReconciliationTest` 和转账申请测试，覆盖并发占用、重复通知、迟到响应、失败/取消及单笔查单异常。无数据库迁移；历史没有流水的订单仍须逐单核对微信记录，本次不自动回填或补发。回滚保留已生成流水，暂停受影响资金入口并继续核对未决结果，不能恢复旧的“跳过后返回成功”通知处理。

发布前备份并执行 [隐藏标记迁移](../database/runner-order-hide.sql)，核对 `SHOW COLUMNS FROM tb_orders LIKE 'publisher_hidden'`，默认值应为 0，再发布依赖新列的 API 和小程序。迁移不回填旧的 `deleted=1` 订单，历史误删需逐单审计并恢复，不能批量解除删除。验证覆盖越权、各在途/资金状态、终态隐藏、重复隐藏、未决资金记录拒绝、图片保留及隐藏后管理端/接单端仍可查询。回滚保留新增列及资金数据；旧版本 DELETE 有越权及全局删除风险，回退前必须停用旧删除入口，不能借回滚清除记录。

### 订单资料与凭证读取权限

用户端按发单人、有效接单人、非参与人分配读取范围：前两者在详情中可查看联系资料、详细地址、清晰任务图片及相应凭证；非参与人可浏览待接单订单的头像、昵称、说明原文、门禁、金额、分类、时间、楼栋和模糊任务图片，不含电话字段、订单号、地址详细位置或清晰图片。说明中的联系方式不额外过滤。大厅统一使用上述浏览范围；详情的 `viewerIsTaker` 由服务端根据当前账号及有效接单记录计算，避免用接单列表第一页判断身份。非参与人的已接单、在途及终态详情请求被拒绝。接单记录须匹配订单、未删除且状态为已接单/配送中/已送达，取消或未知状态不能授权。送达图片另须接单记录已送达。管理员资料读取继续使用独立管理端鉴权入口，不以用户端调用者的管理身份绕过规则。浏览图片解析与回退边界见 `docs/api/media-assets.md`。

详情、筛选列表、联系人、本人接单列表及单独送达图片入口均在私有图片签名前核对权限；清空旧 URL/图片 ID 后仅返回当前授权绑定生成的地址，未绑定时为空，不能退回旧图片列。签名地址是有效期内的访问凭据，已发出的 URL 不能靠服务端角色校验即时撤销；本次防止无关用户取得新地址。验证使用 `RunnerOrderPrivacyTest` 和 `PublicBrowseMapperTest` 覆盖角色、失效接单、公开投影及私有图片解析调用。此修复无需新增迁移；回滚会恢复私人资料暴露风险，回退前应停用相关私有读取入口。小程序需人工验收接单前脱敏预览、接单后详情、联系人及凭证预览。

## 我发布的列表分页

`GET /api/order/my` 按当前登录发单人、现有隐藏标记规则读取，每页默认 20 条，`pageSize` 范围 1–50，`page` 从 1 起。`group` 支持 `all/unpaid/waiting/processing/completed/canceled/refund`，各状态分组与原列表一致；未知状态仍可从全部查询。`keyword` 在 SQL 分页前按原列表的类型、说明、去学校前缀的地址、状态文案、订单号、创建时间和两位金额搜索；空白忽略，百分号与下划线按字面匹配。按创建时间、编号降序稳定排序。

## 我接的列表分页

`GET /api/takeOrders` 每页默认 20 条，`pageSize` 范围 1–50，`page` 从 1 起，仅读取当前账号未删除的接单记录及原有未删除订单。`group` 支持 `all/processing/confirming/settling/completed/canceled/exception`，按现有小程序状态分组：状态 5 且应收款大于零为待收款，无偿状态 5 为已完成，状态 6 已完成，其余未知状态归异常。代买应收包含商品款，普通单只按跑腿费判断。

关键词在分页前按原列表的发单昵称、类型、说明、去学校前缀的地址、状态文案、订单号、发单和接单时间匹配，忽略空白并将 `%/_` 按字面处理。已取消或无效接单的私有说明、地址不参与搜索，也不返回私有联系方式和凭证链接。接单归属及有效状态由同一次查询读取，先校验整页归属再解析媒体；内部授权辅助字段不序列化到响应。

按接单时间、接单编号降序排列。小程序触底续页，搜索和分类重置第一页，失败保留已读页，离开页面或账号/筛选改变后丢弃旧响应。订单、送达与采购凭证各批量读取，头像与分类图标公开批量读取，减少逐条身份和图片查询。此接口与小程序需协调发布；条件查询与未收款汇总等其他入口仍需继续整改，不能认为全部跑腿列表已分页。


## 待办计数与列表分页隔离

“我的”待办及底部红点使用 `GET /api/user/tasks`，服务端只按当前登录账号汇总计数，不下载完整订单和图片，不将某一页的记录数当作总数。返回跑腿待收款、有效待支付、二手买方待办、买方红点、卖方待办和待处理议价数量；只有跑腿待办恰好一条时返回直达订单编号，其他情况下编号为空。

计数沿用现有口径：跑腿待收款保留原接单状态 2、订单状态 5、学校快照及非零跑腿费条件；本次不解决发布/收款额度规则争议。跑腿待支付按原客户端 30 分钟显示窗口排除过期记录，这只是待办展示口径，不修改服务端关单时限。二手买方页面统计状态 0/2，底部红点保留原状态 2 口径；卖方统计状态 1 或状态 8 且 WAIT_USER_CONFIRM；议价统计本人为卖方且状态 0 的记录。界面布局保持，单条直达、多条进列表仍由真实总数决定。

进入“我的”仍读取一页（最多 20 条）未支付订单以保留原客户端超时关单动作，使用 unpaid 分组；不以该页计算数量。服务端既有支付核对/超时任务未变。账号、会话和页面生命周期变化后忽略旧汇总响应，红点缓存按账号会话隔离；汇总失败保留已加载资料并给重试入口。API 与小程序须协调发布，旧版本不识别汇总接口。未执行真实 MySQL、资金链路或界面验收。

## 大厅公开预览分页

游客及未认证用户的大厅使用 `GET /api/order/public` 分页，默认每页 20、最多 50，支持 `page/categoryId/sort/keyword/pickupLabels/receiveLabels`。排序为 `time/price_desc/price_asc`，同价按创建时间及编号降序；空价格按零排序。地址标签参数为 JSON 字符串数组，每侧最多 4 个、每项最多 100 字，以原公开地址的大小写敏感包含规则逐项筛选。关键词忽略首尾空白、保留内部空格，在公开类别、取件地址和收件地址中按字面搜索，`%/_` 不作为通配符。

`GET /api/order/feed` 仅供当前已完成校园认证且有学校的登录账号，用户和学校从登录身份读取。默认每页 20 条、上限 50，`page` 从 1 起；支持 `categoryId/sort/keyword`，价格排序和关键词语义与公开预览一致，另支持 `time_asc`，按创建时间及编号升序供旧时间排序兼容。取件筛选为 `pickCampusNumberId/pickBuildCategoryNumberId/pickBuildingNumberId`，收件筛选为 `receiveCampusNumberId/receiveBuildCategoryNumberId/receiveBuildingNumberId`，使用原地址选择器的 numberId，非空值必须为正数且能解析。两侧地址快照均限定当前学校，分类、双方地址、关键词及全局价格排序均在分页前执行，只取未删除的待接单订单。
