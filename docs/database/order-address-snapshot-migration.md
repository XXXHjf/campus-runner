# 跑腿订单地址快照

订单地址属于下单证据，不能随地址簿或学校、校区、楼栋名称变化。`tb_order_address_snapshot`
以 `(order_id, role)` 唯一保存取件和送达地址；保留原地址 ID、位置 ID、完整展示文字、
不含地址详情的公开摘要、来源及采集时间。没有指向地址簿的级联删除关系。
新订单事务锁定有效地址及其层级，重新核对归属、本校和可用状态，再插入订单和两条快照；
任意一步失败均回滚。后续地址簿编辑、删除以及订单状态更新不修改快照。
发布者、接单者、管理端列表和详情、公开大厅及地址筛选均读快照，不再回查可变地址簿。
联系人姓名和手机号沿用订单已有字段，不从地址簿重新读取。

## 现有数据的边界

迁移脚本为所有订单（包括隐藏及软删除订单）生成两条快照，并读取软删除地址和地点。
`LEGACY_CURRENT` 表示迁移时仍可读取的地址，不能证明它与下单时相同；已编辑地址的原值
不能从当前表恢复。只有可靠的历史备份或审计证据才能用于人工修复，不能据创建时间推测。
`LEGACY_PARTIAL` 保留能找到的部分并显示“历史地址信息不完整”；`LEGACY_MISSING`
显示“历史地址信息缺失”。缺失快照也保留行，因此不会因地址关联失败而隐藏整笔订单。
缺失地址的学校标识保持未知，不借用用户当前学校；相关订单不能凭空进入某个学校的筛选结果。
`SUBMIT` 才是修复上线后下单时保存的快照。
脚本可重复运行，仅补缺失行，不覆盖已有快照，尤其不能将 `SUBMIT` 改成迁移时地址。

## 生产备份及迁移

须执行 [生产操作文档](../deployment/server-operations.md) 的完整发布必检清单。
本变更范围为 API 和新增表，无需改页面、admin 静态文件或 Nginx。
目标环境的版本、表结构、运行开关和数据量须现场只读核实，不能凭本地推断。

1. 安排停写窗口，用既有部署脚本停止 API，并核实无其他 API 实例或写入任务。
   此后不得启动旧 API 继续写入，否则新订单可能缺少快照。
2. 在服务器权限 `700` 的备份目录保存当前 JAR、启动脚本及完整数据库转储。
   使用权限 `600` 的受保护 MySQL 客户端配置传递凭据，禁止将密码放在命令参数或日志中。
   数据库转储使用 `mysqldump --defaults-extra-file=<受保护配置> --single-transaction
   --routines --triggers --events --hex-blob <数据库名>`；确认相关表为 InnoDB。
   转储含姓名、手机和详细地址，权限保持 `600`，不上传 Git。
3. 确认转储退出码、非空文件及校验和，并在隔离库试恢复，核对订单、地址簿和关联地点表数量。
   备份未验证可恢复时停止迁移。
4. 执行 `order-address-snapshot-migration.sql`。MySQL DDL 会隐式提交，不得依赖事务撤销建表。
   核对主键、索引、来源分布及 `orders_without_two_snapshots=0`；快照数应为订单数的两倍。
   只报告计数，不在日志展示地址、联系人或手机。
5. 抽查完整、软删除、缺失和同一地址用作取件/送达的旧订单，明确旧数据恢复边界。
   若发现来源或数量异常，保持 API 停止并排查，不启用新代码。
6. 按生产配置必检和既有脚本部署新版 API，完成数据库探针、HTTPS、登录和订单权限验证。
   使用测试账号确认新订单产生两条 `SUBMIT`，编辑/删除地址后订单地址、列表数量及位置筛选不变；
   公开大厅不含详细地址、联系人、手机号。二手交易地址快照不受影响。

## 回滚

优先停止 API、恢复备份的旧 JAR，再按既有脚本启动和验证，**保留新增快照表及数据**。
新增表不改旧表结构，旧版可读取原订单；但回退旧代码会恢复地址簿依赖，不能称问题已修复。
旧代码运行时新增订单没有快照，再升级时停写并重跑迁移补齐，其来源只能标为迁移证据。

没有业务数据损坏时，不做整库恢复，也不删快照。若必须恢复数据库，先停写、备份当前失败现场，
核对停写点后新增订单、支付、退款和接单记录，制定保留/补录方案；禁止直接用旧转储覆盖新业务。
先在隔离库恢复并核对，之后按已确认的恢复范围执行。
仅在确认所有新增快照已有安全副本、旧 API 已恢复且不再需这些证据时才考虑删除新增表；
通常无需此操作，也不提供自动删表回滚脚本。
